\chapter{Design and Implementation of a Routing Control Platform (RCP)}
\paperinfo{M. Caesar, D. Caldwell, N. Feamster, J. Rexford, A. Shaikh, J. van der Merwe}{NSDI 2005}

\begin{keybox}[RCP in one paragraph]
RCP is a \key{logically centralized} platform, separate from the IP forwarding plane, that collects (i) every BGP route the AS learns from neighbouring ASes and (ii) the internal IGP topology, and then \key{selects the BGP route for each router} in the AS. It talks to routers using the \emph{unmodified iBGP protocol}, so no router changes are needed. Goal: the \key{correctness of full-mesh iBGP} with the \key{scalability of route reflectors}.
\end{keybox}

\section{Why RCP? The problem with iBGP}
\subsection{Route distribution inside an AS}
\begin{itemize}
\item Routers in an Autonomous System (AS) must distribute what they learn about reaching external destinations. Inside the AS this is done with \key{internal BGP (iBGP)}.
\item \key{BGP} is the Internet's interdomain routing protocol. It is prone to protocol oscillation and forwarding loops, is highly sensitive to topology changes inside an AS, and is hard for operators to understand and manage.
\end{itemize}

\subsection{Option 1: full-mesh iBGP --- correct but does not scale}
In a \key{full mesh} there is an iBGP session between every pair of routers. Each router must:
\begin{enumerate}[label=(\roman*)]
\item have an iBGP session with every other router;
\item send BGP update messages to every other router;
\item store a local copy of the advertisements sent by each neighbour for each destination prefix;
\item have a new iBGP session configured whenever a new router is added.
\end{enumerate}
A faster processor and more memory on every router would help, but the installed base of routers lags behind the technology curve and upgrading is costly. Worse, BGP-speaking routers do not always degrade gracefully at their resource limits: they can crash or show persistent routing instability.
\marginnote{``If we increase the memory of the router'' --- not practical, because the installed base lags the technology curve and upgrading is costly. ``If the resource limitation is reached, too much problem!'' --- the router does not just slow down, it can crash or become unstable.}

\subsection{Option 2: route reflectors --- scalable but can be incorrect}
\begin{itemize}
\item iBGP is arranged as a hierarchy of \key{route reflectors}. A route reflector selects a \emph{single} BGP route for each destination prefix and advertises it to its clients.
\item Adding a router only requires sessions to its route reflector(s). This reduces memory and connection overhead on the routers.
\item The cost is correctness: a route reflector \emph{does not necessarily select the same BGP route its clients would have chosen in a full mesh}. Routers along one path through the AS may get different routes from different reflectors, causing \key{inconsistencies}, \key{protocol oscillation} and \key{persistent forwarding loops}.
\item To prevent this, reflectors and clients need a consistent view of the internal topology, which means configuring many routers as reflectors. Large backbones end up with dozens of route reflectors.
\end{itemize}
\marginnote{A route reflector can have more than one client. To reduce inconsistency the number of route reflectors has to be increased, which erodes the scalability benefit.}

\subsection{RCP's central idea}
\paperfig[0.48]{rcp_fig1_as}{RCP in an AS: RCP has an iBGP session (dotted) to each router; routers keep their eBGP sessions to neighbouring ASes.}
\begin{itemize}
\item RCP has a \key{complete view of the available routes and the IGP topology}. It has iBGP sessions with each router; these sessions let RCP learn BGP routes and send each router a routing decision for each destination prefix.
\item Unlike a route reflector, RCP can \key{send a different BGP route to each router}. So each router can be given exactly the route it would have chosen in a full mesh, while the number of iBGP sessions at each router stays independent of network size.
\item Long-term vision: RCP may exchange interdomain routing information with neighbouring domains, while still using iBGP to talk to its own routers.
\end{itemize}
\textbf{Two design goals:}
\begin{enumerate}
\item \key{Consistent route assignment} even when RCP functionality is replicated and distributed for reliability.
\item \key{Fast response to network events} (link failures, external BGP changes), even with many prefixes and routers.
\end{enumerate}
\marginnote{Even if RCP is duplicated, it must work the same way: the same route for the same router, whichever replica computes it.}

\section{Interoperating with existing routers}
\subsection{Three routing protocols and their jobs}
\begin{itemize}
\item \key{eBGP}: exchanges reachability information with neighbouring ASes.
\item \key{iBGP}: propagates that information inside the AS.
\item \key{IGP} (e.g., OSPF, IS-IS): learns how to reach other routers in the same AS. IGPs are link-state protocols with a tunable weight on each link.
\item BGP is a \key{path-vector protocol}: each network prepends its AS number before propagating an announcement.
\item Each router \key{combines} information from these protocols into a forwarding table that maps each destination prefix to the next link in the path. In RCP's design, RCP assigns a single best BGP route per prefix to each router and distributes it with iBGP; the routers still ``merge'' BGP and IGP data to build their forwarding tables.
\end{itemize}
\marginnote{The forwarding table answers ``which is the next link to take?'' It is built from BGP \emph{and} IGP information together, not BGP alone.}

\subsection{BGP route-selection process --- order matters}
\paperfig[0.42]{rcp_fig2_hotpotato}{Three egress routers $W$, $X$, $Y$ connecting to two neighbouring ASes. Solid lines are physical links (with IGP weights); dashed lines are BGP sessions.}

Each router applies the decision process below to the routes learned from its eBGP and iBGP neighbours. The rightmost column records where RCP gets the information for each step (from the handwritten notes and \S3.1.3 of the paper).

\begin{center}
\begin{tabularx}{\linewidth}{@{}c l X@{}}
\toprule
\textbf{Step} & \textbf{Rule} & \textbf{Where the RCS gets this information} \\
\midrule
0 & Ignore if egress router unreachable & IGP view (which egress routers are reachable) \\
1 & Highest local preference & Attribute in the BGP message (set by routing \emph{policy}) \\
2 & Lowest AS-path length & Attribute in the BGP message \\
3 & Lowest origin type & Attribute in the BGP message \\
4 & Lowest MED (same next-hop AS) & Attribute in the BGP message \\
5 & eBGP-learned over iBGP-learned & A bit of logic: a route is eBGP-learned for the router that sent it to RCP, iBGP-learned for all others \\
6 & Lowest IGP path cost to egress & IGP view (path costs from the IGP Viewer) \\
7 & Lowest router ID of BGP speaker & Known because the BGP Engine has an iBGP session with every router \\
\bottomrule
\end{tabularx}
\end{center}
In the simplest case a router picks the shortest AS path (step 2) and breaks ties by router ID (step 7). Other steps depend on route attributes such as local preference, which is assigned by routing policies configured on the border routers. RCP must handle the fact that border routers apply policies to routes learned from eBGP neighbours and that all routers run route selection on what they learn.
\marginnote{``Local pref comes from policies.'' ``Some steps depend on the route attributes.'' \textbf{New learning:} hot-potato routing does \emph{not} mean the decision process starts from the IGP. The decision steps are still performed in order; IGP cost comes in very late (step 6).}

\subsection{Hot-potato (early-exit) routing}
\begin{itemize}
\item Often several routes are equally good up to step 5. In the figure above, router $Z$ learns routes with the same AS-path length from $W$, $X$, $Y$. Step 6 picks the \key{closest egress router by IGP cost}: $Z$ chooses $X$ (cost 2). This is \key{early-exit} or \key{hot-potato routing}.
\item RCP therefore needs a \key{real-time view of the IGP topology} to pick the closest egress for every prefix on behalf of every router. When the topology changes, RCP must work out which routers should change egress.
\item \textbf{Challenge:} one IGP change can make many routers change BGP decisions for many prefixes. If link $V$--$X$ goes from weight 1 to 3, $Z$ switches to egress $Y$. Hot-potato changes cause large, unpredictable traffic shifts, plus long convergence delays because routers must revisit BGP decisions for many prefixes (one to two minutes is not uncommon).
\item To implement hot-potato routing, RCP must determine the influence of an IGP change on every router for every prefix. The authors see RCP as a way to \key{move beyond hot-potato routing} toward more flexible egress selection (\S\ref{sec:rcp-decouple}).
\end{itemize}
\marginnote{Think of something else instead of hot-potato: a small IGP change produces a large traffic shift.}

\section{RCP architecture}
\paperfig[0.48]{rcp_fig3_arch}{RCP interacts with routers using standard protocols: IGP adjacencies (solid lines) and iBGP sessions with every router (dashed). RCP can obtain information from separate network partitions $P_1$, $P_2$.}

\subsection{The three modules}
To compute what each router would have picked in a full mesh, RCP needs both the IGP topology and the best route to each destination from every router that learns a route from a neighbouring AS. So it has three modules:
\begin{enumerate}
\item \key{IGP Viewer}: establishes IGP adjacencies with one or more routers and receives IGP topology information.
\item \key{BGP Engine}: learns BGP routes from the routers and sends the RCS's route assignments back to each router.
\item \key{Route Control Server (RCS)}: uses the IGP topology from the IGP Viewer and the BGP routes from the BGP Engine to compute the best BGP route for each router.
\end{enumerate}
\marginnote{IGP Viewer $\leftrightarrow$ routers: IGP adjacencies. BGP Engine $\leftrightarrow$ routers: iBGP sessions. Best BGP route = IGP view + BGP Engine information!}

\subsection{IGP connectivity graph and partitions}
The routers $R$ of the AS form an IGP connectivity graph $G=(R,E)$, where $E$ are the IGP links.
\begin{itemize}
\item The IGP topology is usually one connected component, but link, router or interface failures occasionally create \key{partitions}: $G=\{P_1,P_2,\ldots,P_n\}$.
\item \key{The RCS only computes routes for partitions $P_i$ for which it has complete IGP and BGP information}, and it computes routes for each partition independently.
\end{itemize}
\marginnote{RCS works partition-wise! Partitions are within an AS. Everything is working at the partition level.}

\subsection{IGP Viewer}
\begin{itemize}
\item Monitors the IGP topology and provides it to the RCS. It forms IGP adjacencies to receive the IGP's \key{link-state advertisements (LSAs)}.
\item To make sure the IGP Viewer \key{never routes data packets}, the links between the Viewer and the routers get \key{large IGP weights}, so the Viewer is never an intermediate hop on a shortest path.
\item OSPF and IS-IS use \key{reliable flooding} of LSAs. So the Viewer can receive LSAs from \emph{all} routers in a partition by having an adjacency to just \emph{one} router in that partition.
\end{itemize}
\textbf{Observation 1.} \emph{The IGP Viewer has the complete IGP topology for all partitions that it connects to.}
\begin{itemize}
\item The Viewer computes \key{pairwise shortest paths} for all routers and gives the RCS only the \emph{path costs}; it need not send each IGP edge weight. The RCS uses these costs to decide, for any router, which egress router is closest.
\item \key{Grouping}: sometimes a group of routers always uses the same egress (e.g., access routers in a city that all leave through one gateway). Because the Viewer knows the topology, it can determine which routers should get the same BGP route (e.g., routers in one OSPF ``area''). Grouping reduces the number of independent route computations the RCS must do. An operator can also dictate the grouping.
\end{itemize}
\marginnote{LSAs share the local network topology. Large IGP weights $\Rightarrow$ the Viewer avoids routing data packets. Due to flooding, a connection with a single router is sufficient! Grouping exploits this property to reduce route computation for the RCS.}

\subsection{BGP Engine}
\begin{itemize}
\item Maintains an \key{iBGP session with each router} in the AS. These sessions let RCP (1) learn about candidate routes and (2) communicate its routing decisions.
\item iBGP runs over \key{TCP}, so the BGP Engine need not be physically adjacent to a router: it can maintain sessions with any router reachable through the IGP topology.
\end{itemize}
\textbf{Observation 2.} \emph{A BGP Engine can establish iBGP sessions to all routers in the IGP partitions that it connects to.}
\begin{itemize}
\item Assumption: IGP connectivity between two endpoints is enough to establish a BGP session. Persistent congestion or misconfiguration can break this, but those cases are anomalous; routers often put BGP packets in a high-priority queue.
\item BGP updates carry a \key{``next hop''} attribute. The BGP Engine can advertise routes whose next hop is \emph{another router} in the network, so \key{the BGP Engine does not need to forward data packets}. The RCS can send a route with the next-hop attribute unchanged; routers then forward packets toward the egress router.
\item A router sends updates to the BGP Engine only when it selects a new best route learned from a neighbouring AS. The BGP Engine only sends an update when a router's decision should change. Unlike a route reflector, it can send a different route to each router.
\end{itemize}
\marginnote{iBGP $\rightarrow$ TCP. Observation 2 holds within a partition! The next-hop attribute is set by the RCS; the BGP Engine has no role in forwarding. Only update messages are exchanged.}

\subsection{Route Control Server (RCS)}
\begin{itemize}
\item Receives IGP topology from the IGP Viewer and BGP routes from the BGP Engine, computes routes for a \emph{group} of routers, and returns the assignments through the BGP Engine.
\item It does not send a route to a router that has already chosen a route ``better'' than all candidates under the decision process.
\end{itemize}
\textbf{Observation 3.} \emph{An RCS can only make routing decisions for routers in a partition for which it has both IGP and BGP routing information.}

\textbf{Emulating full mesh.} A reasonable approach is for the RCS to send each router the route it would have selected in a full-mesh configuration, by \key{executing the BGP decision process on behalf of each router}. It can do this because: (1) knowing the IGP topology, it knows which egress routers are reachable from each router; (2) steps 1--4 compare attributes in the BGP messages; (3) for step 5 it treats a route as eBGP-learned for the router that sent it and iBGP-learned for the others; (4) for step 6 it uses IGP path costs from the Viewer; (5) for step 7 it knows each router's ID from the iBGP session.
\marginnote{Emulating full-mesh behaviour ensures the best route is selected. How can RCP perform this? It runs the normal decision process per router, using complete IGP and BGP inputs. If a group can be formed (e.g., routers $r_1,\ldots,r_4$ all exiting via one egress), the RCS computes once for the whole group.}

\section{Correctness: route validity and path visibility}
\subsection{Route validity: two invariants}
The RCS must not assign routes that create forwarding loops, blackholes, or other anomalies. Two invariants must hold:
\begin{enumerate}
\item \key{Same-egress invariant:} the routers along the shortest IGP path from any router to its assigned egress must be assigned a route with the \emph{same} egress router.
\item \key{Partition invariant:} the IGP path to a route's next hop must only traverse routers in the \emph{same partition} as the next hop.
\end{enumerate}
\textbf{Why emulating full mesh satisfies both:}
\begin{itemize}
\item In a full mesh each router picks the egress with the shortest IGP path, and all routers along that shortest path also pick the same closest egress. So invariant 1 holds.
\item The RCS never assigns an egress router in some other partition. So invariant 2 holds.
\end{itemize}
The RCS has flexibility in assigning paths, but must guarantee these properties even when it is not emulating a full mesh.
\marginnote{The two invariants in simple language: (1) ``Don't change the egress while walking toward the egress.'' (2) ``Don't leave the partition while walking toward the BGP next hop.'' Each RCS works within its own partition (\emph{apni partition mein kaam karta hai}).}

\subsection{Path visibility and replication}
\begin{itemize}
\item \key{Path visibility:} every router should be able to exchange routes with at least one RCS, and should receive some route to an external destination if one exists.
\item So each partition needs at least one IGP Viewer, one BGP Engine and one RCS. Replicating these modules makes it less likely that a group of routers is cut off from all instances.
\item If the RCS is replicated, two replicas may assign routes to routers on the same IGP path, so they \key{must make consistent decisions}. Route computation must be \key{deterministic}: the same IGP topology and BGP inputs always produce the same outcome.
\item A router partitioned from RCP is no worse off than a router that cannot reach its route reflector today; it can often still route with its eBGP-learned routes.
\end{itemize}
\marginnote{Module replicas must select the same thing even if they are different instances.}

\section{Consistency with distributed RCP}
\paperfig[0.62]{rcp_fig4_timeline}{Periods during convergence for a single destination. Routes are stable most of the time, with transient periods caused by IGP or eBGP events. The analysis is about the steady state.}
\begin{itemize}
\item To survive partitions and avoid a single point of failure, RCP modules should be \key{replicated}. Replicas may then have different views of the network state, and inconsistencies may be \key{transient} or \key{persistent}; if routers learn routes from different replicas, this could cause routing loops.
\item This seems to call for a \key{consistency protocol}. The surprising result: \key{no consistency protocol is required} to prevent persistent inconsistencies.
\end{itemize}

\subsection{Transient vs.\ persistent inconsistencies}
\begin{itemize}
\item Replicas receive BGP and IGP updates at different times, so for a while they may make different decisions for the same routers. During these transient periods routes may be inconsistent.
\item On a per-prefix basis, long transient periods are not the common case. BGP update traffic overall is fairly continuous, but for a \emph{single destination} as seen by one AS it is bursty with long silences; over hours, routes to external destinations are stable.
\item So the paper analyses consistency \emph{after the transient period has ended}. Any intra-AS routing protocol, iBGP included, is temporarily inconsistent while BGP and IGP routes change. Comparing RCP's transient behaviour with iBGP's is left as future work.
\end{itemize}
\marginnote{During these (eBGP/IGP) events routes may be inconsistent! BGP update message traffic for one destination is very bursty. Transient comparison = future work.}

\subsection{RCP replicas are consistent in steady state}
\textbf{Proposition 1.} \emph{If multiple RCSes assign paths to routers in partition $P_i$, then each router in $P_i$ receives the same route assignment from each RCS.}

\textbf{Proof.} Two RCSes can only assign different routes to a router in $P_i$ if they receive \emph{different inputs} (BGP routes from different routers, or different IGP views). Suppose RCSes $A$ and $B$ both assign routes to some router in $P_i$. By Observation 1 both have the IGP topology for \emph{all} routers in $P_i$; by Observation 2 they also have complete BGP information. By Observation 3 both can assign routes to all routers in $P_i$. Since they have the same inputs and the computation is deterministic, they make the same assignment to every router in $P_i$. \hfill$\blacksquare$
\marginnote{Simple proof: both replicas will have the same IGP view, and both BGP Engines see the same routes, so they compute the same result. The (consistency) protocol is not necessary! $P_i$ = partition.}

\subsection{Failure caveat: liveness vs.\ correctness}
Some failures can violate Observation 2: IGP connectivity exists between a BGP Engine and a router, but the iBGP session fails (congestion, misconfiguration, software failure). Then two RCSes may hold BGP information from different subsets of routers in the partition. By design, \emph{neither} assigns routes to any router in that partition, even though together they have complete information.
\begin{itemize}
\item This affects \key{liveness}: replicas may fail to assign routes even when they collectively have complete information.
\item It never affects \key{correctness}: two RCSes never assign different routes to the same router.
\end{itemize}
\marginnote{The whole partition gets no routes (\emph{poore partition ko nahi milega kuch}). Failing to reach the backup does not affect correctness --- correctness always holds; only liveness is affected.}

\section{RCS implementation}
\paperfig[0.5]{rcp_fig5_rcs}{RCS processing. Left: on a BGP update, update RIB-In and re-select the route for each router. Right: on an IGP path-cost change for egress $X$, re-rank the egress list and re-evaluate only the affected prefixes.}
Backbone ASes have many routers (500--1000) and prefixes (150,000--200,000), so scalability and efficiency are the main challenges.
\subsection{Data structures}
\begin{itemize}
\item Incoming BGP updates are stored in a \key{Routing Information Base (RIB-In)}. The RCS performs per-router route selection and stores the selected routes in a \key{per-router RIB-Out}.
\item RIB-In and RIB-Out are \key{tries} indexed by prefix. RIB-In keeps the list of routes learned for each prefix; each route's \key{next-hop} uniquely identifies the egress router where it was learned.
\item The RCS also receives the IGP path cost for each pair of routers, and uses RIB-In to compute the best route for each router using the path costs in steps 0 and 6. The result goes to the BGP Engine, which sends the update to the router.
\item Path-cost changes from the OSPF Viewer may require recomputation when step 6 selected the route and the cost to the selected egress changes. Finding the affected routes efficiently is the hard part.
\end{itemize}
\marginnote{RIB-Out is a per-router table. Changes introduced by the IGP Viewer cause recomputation!}

\paperfig[0.62]{rcp_fig6_ribs}{RCS data structures: one global RIB-In (with back pointers), per-router RIB-Out shadow tables that point into it, and per-router egress lists sorted by IGP cost, each with a ``using table''.}

\subsection{Optimization 1: store only a single copy of each BGP route}
\begin{itemize}
\item Storing a copy of every router's routes for every prefix would need huge memory. The RCS stores each route \emph{once}, in RIB-In.
\item On an update, the RCS indexes RIB-In by prefix and adds, updates or removes the route identified by its next-hop.
\item RIB-Out is implemented as per-router \key{shadow tables}: prefix-indexed tries containing \emph{pointers} into RIB-In. In the figure above, router1 is assigned route1 for prefix2, while router2 and router3 are both assigned route2.
\end{itemize}
\marginnote{This (RIB-In) gets updated, and everything referencing this table sees the update automatically. The next hop acts like an ID that identifies the egress.}

\subsection{Optimization 2: keep track of routers assigned each route}
\begin{itemize}
\item Each RIB-In route has \key{back pointers} to the routers assigned that route.
\item On a \key{withdrawal} of the prefix from a next hop, the RCS reruns the decision process only for the routers in this list, using the remaining routes in RIB-In.
\item This does \emph{not} work for BGP \key{announcements}: a new route may be better for anyone, so the RCS must recompute the assignment for every router.
\end{itemize}
\marginnote{When withdrawn, only the routers in that list are recomputed (not all). On a new announcement, every router must be recomputed.}

\subsection{Optimization 3: rank egress routers by IGP path cost}
\begin{itemize}
\item One IGP path-cost change can affect BGP decisions for many prefixes. To avoid revisiting every prefix, the RCS keeps, for each router, a \key{ranking of egress points sorted by IGP path cost} (the ``egress lists'').
\item For each egress, the RCS stores pointers to the prefixes and routes in RIB-Out that use it: the \key{using table}. E.g., router1 uses eg1 for prefix2 and prefix3.
\item If router1's cost to eg1 \emph{increases}, eg1 moves down the list until it meets an egress with higher cost. The RCS recomputes only the prefixes in eg1's using table.
\item If eg3 \emph{becomes} router1's closest egress, it moves to the top, and the RCS recomputes only the prefixes of the egresses ``passed over'' (eg1, eg2), since they may now prefer eg3.
\end{itemize}
\marginnote{The using table tells which routes are using this egress. Only recompute for those prefixes that were using this egress --- this is the optimization.}

\subsection{Optimization 4: assign routes to groups of related routers}
\begin{itemize}
\item The RCS can assign the same route for a prefix to a \key{group} of routers. Groups come from the IGP Viewer or are configured by the operator.
\item RIB-Out and egress-list entries are then per group, giving a large reduction in storage and CPU. The RCS keeps the list of routers in each group so the BGP Engine can send the route to every member.
\item \textbf{Trade-off:} less overhead versus less flexibility to give different routes to routers in the same group.
\item The prototype uses Points-of-Presence (PoPs, matching OSPF areas) as groups, treating each PoP as one node.
\end{itemize}
\marginnote{Grouping: the group identifier comes from the IGP Viewer, or it is done manually by the operator. We reduce the flexibility to assign different routes within a group!}

\section{IGP Viewer instance: the OSPF Viewer}
\paperfig[0.55]{rcp_fig7_ospf}{LSA processing in the OSPF Viewer. Refresh LSAs are dropped; change LSAs go through the intra-area stage (1) and the inter-area stage (2), and only path-cost and group changes reach the RCS.}
The OSPF Viewer connects to one or more routers to receive LSAs, keeps an up-to-date topology, and computes the path cost for each pair of routers. It offloads the RCS in two ways.

\subsection{Send only path-cost changes to the RCS}
\begin{itemize}
\item OSPF periodically \key{refreshes} LSAs even when the network is stable. The Viewer keeps a \key{topology model} and uses it to tell whether an LSA is a real change or just a refresh; refresh LSAs are filtered because the RCS need not act on them.
\item For a \key{change LSA}, the Viewer runs shortest-path-first (SPF) calculations from each router's viewpoint, then passes \emph{only the path costs that changed} (the ``path cost change calculation'' stage).
\end{itemize}
\marginnote{Only pass the costs that changed.}

\subsection{OSPF areas: why the SPF runs in two stages}
\begin{itemize}
\item For scalability an OSPF domain may be divided into \key{areas} in a hub-and-spoke layout. \key{Area 0} (the backbone) is the hub and connects the non-backbone areas (spokes). Each link belongs to exactly one area. Routers with links in several areas are \key{border routers}.
\item A router learns the full topology of the areas it has links in through \key{intra-area LSAs}. It does \emph{not} learn the topology of remote areas; instead it learns the total cost of paths to nodes in remote areas from each border router through \key{summary LSAs}.
\item OSPF mandates that if two routers are in the same area, the path between them must stay within the area, \emph{even if a shorter path exists through another area}. So the Viewer cannot ignore area boundaries and run one SPF over the whole topology.
\item It computes in \key{two stages}: (1) \emph{intra-area stage} --- path costs within each area separately, using intra-area LSAs; (2) \emph{inter-area stage} --- path costs between routers in different areas, by combining paths from the individual areas.
\item If the Viewer sees only some areas, it does the intra-area stage for visible areas and uses summary LSAs from border routers to get costs to routers in non-visible areas during the inter-area stage.
\end{itemize}
\marginnote{Area boundaries are important. OSPF does not perform SPF over the entire topology. (1) intra-area LSA, (2) inter-area/summary LSA. Hub = Area 0 (A0), spokes = A1, A2, A3 joined by border routers. Summary LSAs help with grouping.}

\subsection{Reduce RCS overhead by combining routers into groups}
The OSPF Viewer (i) provides path-cost information for all Area 0 routers (which includes the border routers in non-zero areas), and (ii) forms one \key{group per non-zero area} and supplies the group membership. As a bonus, the Viewer needs no physical connection to non-zero areas: summary LSAs from Area 0 let it compute path costs from every Area 0 router to every other router, and also determine the groups. Grouping is internal to RCP and needs no protocol or configuration changes on routers.

\section{BGP Engine implementation}
The BGP Engine receives BGP messages from routers and passes them to the RCS, and receives RCS instructions to send routes to individual routers. It is built by modifying the Quagga software router to store outbound routes per router and to take assignments from the RCS instead of computing them. Two design insights:
\begin{itemize}
\item \key{Cache BGP routes for efficient refreshes.} The BGP Engine keeps a local cache of RIB-In and RIB-Out. The RIB-In cache lets it give the RCS a fresh copy of all routes without touching the routers, which makes it easy to add a new RCS replica or recover from an RCS failure. The RIB-Out cache lets it re-send assignments to operational routers without involving the RCS, which helps after a temporary loss of iBGP connectivity. Since routes are assigned per router, it keeps a RIB-Out for each router.
\item \key{Manage the low-level communication with the routers.} It provides a simple, stable layer that maintains BGP sessions with the routers, handles the many TCP connections and the details of establishing BGP sessions, and multiplexes update messages into a single stream to and from the RCS.
\end{itemize}

\section{Decoupling BGP from IGP}\label{sec:rcp-decouple}
\begin{itemize}
\item RCP handles BGP updates quickly, but \key{processing internal topology changes is the challenge}. One event (e.g., a link failure) changes IGP path costs for many router pairs, which can change BGP assignments for many routers and prefixes. This coupling is fundamental to how hot-potato routing uses IGP cost.
\item Router vendors face the same problem. Some do not run the BGP decision process after IGP events; they \key{periodically scan} the BGP table instead (e.g., every 60 seconds). This can leave inconsistencies that cause forwarding loops for tens of seconds; scanning more often increases router load.
\item RCP faces a \emph{larger} challenge because it computes routes for many routers. Software optimization helps but cannot remove the problem.
\item Proposal: use RCP to \key{move beyond hot-potato routing}. Today a small IGP event can trigger a large, abrupt traffic shift; RCP should prevent such shifts unless they are needed to avoid congestion or delay.
\item Experiment idea: in a ``BGP-free'' core (e.g., MPLS or any tunnelled network) RCP can direct an ingress router to any egress with a route, and keep that assignment across internal topology changes. RCP then reacts only to path-cost changes that affect the availability of tunnel endpoints. Ignoring the others cut decision time dramatically (from minutes to well under a second in the paper's trace).
\end{itemize}

\section{Fast revision checklist}
\begin{itemize}
\item \key{Full mesh:} correct, but sessions and update/storage overhead grow with the number of routers.
\item \key{Route reflector:} scalable, but may pick a route its clients would not, causing inconsistency, oscillation and loops.
\item \key{RCP:} logically centralized; unmodified iBGP; can send a different route to each router; emulates full-mesh decisions.
\item \key{Modules:} IGP Viewer (adjacencies, LSAs, path costs, groups); BGP Engine (iBGP over TCP, caches, session management); RCS (per-router/per-group route selection).
\item \key{Decision process:} steps 0--7 in order; hot-potato is step 6 (IGP cost), not the start of the process.
\item \key{Observations 1--3:} Viewer sees full topology of connected partitions; BGP Engine reaches all routers there; RCS decides only where it has both.
\item \key{Invariants:} same egress along the path; never leave the partition on the way to the next hop.
\item \key{Proposition 1:} replicas deciding for the same partition have identical inputs $\Rightarrow$ identical outputs. No consistency protocol needed.
\item \key{Liveness vs.\ correctness:} failures may stop route assignment (liveness), never cause conflicting assignments (correctness).
\item \key{RCS optimizations:} single route copy + shadow RIB-Out pointers; back pointers for withdrawals; IGP-cost egress ranking with using tables; groups.
\item \key{OSPF Viewer:} drop refresh LSAs; send only changed costs; two-stage SPF respecting areas; summary LSAs for non-visible areas and grouping.
\item \key{Decoupling:} react only to the IGP changes that matter, to avoid abrupt hot-potato traffic shifts.
\end{itemize}
