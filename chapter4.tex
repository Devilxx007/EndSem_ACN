\chapter{P4: Programming Protocol-Independent Packet Processors}
\paperinfo{P. Bosshart, D. Daly, G. Gibb, M. Izzard, N. McKeown, J. Rexford, C. Schlesinger, D. Talayco, A. Vahdat, G. Varghese, D. Walker}{ACM SIGCOMM CCR, Vol.\ 44 No.\ 3, July 2014}

\begin{keybox}[P4 in one paragraph]
\key{P4 is a high-level language for programming protocol-independent packet processors.} It \key{works in conjunction with} SDN control protocols like \key{OpenFlow}. OpenFlow explicitly specifies the protocol headers it operates on, and this set has grown from 12 to 41 fields. P4 is a strawman proposal for \key{how OpenFlow should evolve}: the controller should \emph{tell the switch how to operate} (how to parse and process packets), instead of being constrained by a fixed switch design. Three goals: \key{reconfigurability}, \key{protocol independence}, \key{target independence}.
\end{keybox}

\section{Motivation}
\begin{itemize}
\item \key{Software-Defined Networking (SDN) gives operators programmatic control} over their networks. \key{In SDN, the control plane is physically separate from the forwarding plane, and one control plane controls multiple forwarding devices.} A common, open, vendor-agnostic interface (like OpenFlow) lets a control plane manage devices from different vendors.
\item \key{OpenFlow started simple}, with a \key{single table of rules that could match packets on a dozen header fields} (MAC addresses, IP addresses, protocol, TCP/UDP ports\ldots). \key{Over the past five years the specification has grown increasingly more complicated}, with \key{many more header fields} and multiple stages of rule tables:
\end{itemize}
\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Version} & \textbf{Date} & \textbf{Header fields} \\
\midrule
OF 1.0 & Dec 2009 & 12 fields (Ethernet, TCP/IPv4) \\
OF 1.1 & Feb 2011 & 15 fields (MPLS, inter-table metadata) \\
OF 1.2 & Dec 2011 & 36 fields (ARP, ICMP, IPv6, etc.) \\
OF 1.3 & Jun 2012 & 40 fields \\
OF 1.4 & Oct 2013 & 41 fields \\
\bottomrule
\end{tabular}
\end{center}
\begin{itemize}
\item New fields keep coming: data-centre operators want new encapsulations (NVGRE, VXLAN, STT) and resort to software switches that are easier to extend.
\item \key{Rather than repeatedly extending the OpenFlow specification}, \key{future switches should support flexible mechanisms for parsing packets and matching header fields}, exposed through a common, open interface --- \key{a new ``OpenFlow 2.0'' API}. This would be simpler, more elegant and \key{more future-proof}.
\item Recent chips show such flexibility is possible at terabit speeds, but \key{programming this new generation of switch chips is far from easy}: \key{each chip has its own low-level interface}, akin to microcode.
\end{itemize}

\paperfig[0.48]{p4_fig1_config}{P4 is a language to \emph{configure} switches (parser and tables, via a compiler), while classic OpenFlow-style APIs \emph{populate} the tables at run time (installing and querying rules, via a rule translator).}
Figure above: \key{P4 is used to configure a switch, telling it how packets are to be processed}, while \key{existing APIs (such as OpenFlow) are designed to populate the forwarding tables in fixed-function switches}. \key{P4 raises the level of abstraction} for programming the network and can serve as a general \key{interface between the controller and the switches}.

\section{The three goals of P4}
\begin{enumerate}
\item \key{Reconfigurability.} \key{The controller should be able to redefine the packet parsing and processing in the field}, i.e., programmers can change the way switches process packets once they are deployed.
\item \key{Protocol independence.} \key{The switch should not be tied to specific packet formats} or network protocols. The controller should be able to \key{specify (i) a packet parser for extracting header fields with particular names and types, and (ii) a collection of typed match+action tables that process these headers}.
\item \key{Target independence.} Just as a C programmer need not know the specifics of the CPU, the controller programmer should not need the details of the switch. \key{A compiler should take the switch's capabilities into account when turning a target-independent description (written in P4) into a target-dependent program} (used to configure the switch).
\end{enumerate}
The key challenge is a ``sweet spot'' balancing expressiveness against ease of implementation across many hardware and software switches.

\section{Abstract forwarding model}
\paperfig[0.62]{p4_fig2_model}{The abstract forwarding model: a programmable parser, then ingress match+action stages, a buffer, and egress match+action stages. The switch configuration (parse graph, control program, table config, action set) is set by P4; the tables' forwarding rules are populated at run time.}
In the abstract model, \key{switches forward packets via a programmable parser followed by multiple stages of match+action, arranged in series, parallel, or a combination of both}. Derived from OpenFlow, the model makes three generalizations:
\begin{enumerate}
\item \key{OpenFlow assumes a fixed parser, whereas this model supports a programmable parser} so new headers can be defined.
\item \key{OpenFlow assumes the match+action stages are in series, whereas here they can be in parallel or in series.}
\item Actions are composed from protocol-independent primitives supported by the switch.
\end{enumerate}
The model generalizes packet processing across devices (Ethernet switches, load-balancers, routers) and technologies (fixed-function ASICs, NPUs, reconfigurable switches, software switches, FPGAs), so a common language can describe them and a compiler can map programs to each.

\subsection{Configure vs.\ populate}
The \key{forwarding model is controlled by two types of operations: Configure and Populate}.
\begin{itemize}
\item \key{Configure} operations \key{program the parser, set the order of match+action stages, and specify the header fields processed by each stage}. Configuration \key{determines which protocols are supported and how the switch may process packets}.
\item \key{Populate} operations \key{add (and remove) entries to the match+action tables that were specified during configuration}. Population \key{determines the policy applied} to packets at any given time.
\end{itemize}
The paper assumes the \key{switch need not process packets during configuration}, but expects \key{implementations to allow packet processing during partial or full reconfiguration, enabling upgrades with no downtime}; the model deliberately allows \key{reconfiguration that does not interrupt forwarding}. For fixed-function ASICs the configuration phase has little meaning: \key{the compiler's job is simply to check if the chip can support the P4 program}.

\subsection{Parser, ingress and egress}
\begin{itemize}
\item Arriving packets are \key{first handled by the parser}. \key{The packet body is assumed to be buffered separately, and is unavailable for matching.} The \key{parser recognizes and extracts fields from the header}, which defines the protocols the switch supports. The model makes no assumption about what headers mean; \key{the parsed representation defines a collection of fields on which matching and actions operate}.
\item The \key{extracted header fields are then passed to the match+action tables}, which are \key{divided between ingress and egress}. Both may modify the header.
\item \key{Ingress match+action determines the egress port(s) and the queue} into which the packet is placed. \key{Based on ingress processing, the packet may be forwarded, replicated} (for multicast, span, or to the control plane), \key{dropped, or trigger flow control}.
\item \key{Egress match+action performs per-instance modifications to the packet header} --- e.g., different for each multicast copy.
\item Action tables (counters, policers, etc.) can be associated with a flow to track frame-to-frame state.
\end{itemize}

\subsection{Metadata and queueing}
\begin{itemize}
\item \key{Packets can carry additional information between stages, called \emph{metadata}}, treated just like packet-header fields. \key{Examples: the ingress port, the transmit destination and queue, a timestamp used for packet scheduling, and data passed from table to table that does not involve changing the parsed representation of the packet, such as a virtual network identifier.}
\item Queueing works as in OpenFlow: \key{an action maps a packet to a queue, which is configured to receive a particular service discipline} (e.g., minimum rate, DRR), chosen as part of switch configuration.
\item (Beyond scope:) primitives could be added for congestion control, e.g., setting the ECN bit under new conditions.
\end{itemize}

\section{Why a new language? Table dependencies}
The language must say how the parser knows which header formats to expect (declare header types and legal header sequences) and how headers are processed (e.g., decrement and test TTL, add tunnel headers, compute checksums). This motivates an \emph{imperative control-flow program} over declared header types and a primitive set of actions.

\textbf{Why not Click?} Click builds switches from modules of arbitrary C++. It is extremely expressive and good for CPU kernels, but \emph{insufficiently constrained}: it does not mirror the parse--match--action pipelines of hardware, is not designed for a controller--switch architecture with tables populated at run time by well-typed rules, and makes it hard to infer the dependencies that limit parallel execution.

\paperfig[0.62]{p4_fig3_tdg}{Table dependency graph (TDG) for an L2/L3 switch: each node is a match+action table (its match fields and actions); edges show data and control dependencies (e.g., routing hit/miss).}
\begin{itemize}
\item \key{A packet-processing language must allow the programmer to express (implicitly or explicitly) any serial dependencies between header fields.} \key{Dependencies determine which tables can be executed in parallel.} For example, \key{sequential execution is required for an IP routing table and an ARP table} because of the data dependency between them.
\item Dependencies are found by analysing \key{Table Dependency Graphs (TDGs)}; \key{these graphs describe the field inputs, actions and control flow between tables}. TDG nodes map directly to match+action tables, and dependency analysis tells where each table can sit in the pipeline.
\item But programmers think imperatively, not in graphs. Hence a \key{two-step compilation process}: \key{at the highest level, programmers express packet processing} in an imperative language describing control flow (P4); \key{below this, a compiler translates the P4 representation to TDGs} for dependency analysis, and then maps the TDG to a specific target. P4 is designed \key{to make it easy to translate a P4 program into a TDG}.
\end{itemize}
\begin{keybox}[Sweet spot]
P4 sits between the generality of Click (hard to infer dependencies and map to hardware) and the inflexibility of OpenFlow 1.0 (impossible to reconfigure protocol processing).
\end{keybox}

\section{P4 language by example: mTag}
\subsection{Problem setting}
An L2 data-centre network has top-of-rack (ToR) switches at the edge and a two-tier core. End-hosts are growing and \textbf{core L2 tables are overflowing}. MPLS would simplify the core, but a label-distribution protocol with multiple tags is daunting. PortLand needs MAC rewriting (breaking debugging tools) and new agents answering ARP.

\textbf{mTag} combines PortLand's hierarchical routing with simple MPLS-like tags. Routes through the core are encoded in a \textbf{32-bit tag of four one-byte fields}; it can carry a ``source route'' or a destination locator (like PortLand's pseudo-MAC). \textbf{Each core switch examines only one byte} of the tag, chosen by its position in the hierarchy and the direction (up/down). The first ToR switch adds the tag (an end-host NIC could too).

\subsection{P4 concepts: the program components}
\begin{itemize}
\item \key{Headers}: \key{a header definition describes the sequence and structure of a series of fields}, including field widths and constraints on values.
\item \key{Parsers}: \key{a parser definition specifies how to identify headers} and valid header sequences in packets.
\item \key{Tables}: \key{match+action tables} are the mechanism for processing; the program defines the fields a table may match and the actions it may execute.
\item \key{Actions}: \key{P4 supports construction of complex actions from simpler protocol-independent primitives}; these are available inside tables.
\item \key{Control programs}: \key{the control program determines the order of match+action tables applied to a packet} --- a simple imperative program describing control flow between tables.
\end{itemize}

\subsection{Header formats}
Each header is an ordered list of field names with widths (optionally constrained). The mTag header is added without changing existing declarations; its field names show two aggregation layers in each direction.
\begin{lstlisting}
header ethernet {
  fields {
    dst_addr : 48;  // width in bits
    src_addr : 48;
    ethertype : 16;
  }
}
header vlan {
  fields { pcp : 3; cfi : 1; vid : 12; ethertype : 16; }
}
header mTag {
  fields {
    up1 : 8; up2 : 8; down1 : 8; down2 : 8;
    ethertype : 16;
  }
}
\end{lstlisting}

\subsection{The packet parser}
P4 assumes the switch can implement a \emph{state machine} that walks headers from start to finish, extracting field values; transitions are chosen by values in the current header. \key{Upon reaching a state for a new header, the state machine extracts the header using its specification and proceeds to identify its next transition.} \key{The extracted headers are forwarded to match+action processing in the back half of the pipeline.}
\begin{lstlisting}
parser start { ethernet; }
parser ethernet {
  switch(ethertype) {
    case 0x8100: vlan;
    case 0x9100: vlan;
    case 0x800:  ipv4;
    // Other cases
  }
}
parser vlan {
  switch(ethertype) {
    case 0xaaaa: mTag;
    case 0x800:  ipv4;
  }
}
parser mTag {
  switch(ethertype) { case 0x800: ipv4; }
}
\end{lstlisting}
Parsing starts at \texttt{start} and ends at an explicit stop state or an unhandled case (possibly an error). This parser has four states; real parsers can have over a hundred.

\subsection{Table specification}
\key{The programmer describes how the defined header fields are to be matched} (\key{exact, ranges, or wildcards?}) and \key{what actions should be performed when a match occurs}. The edge switch matches the L2 destination and VLAN ID and selects an mTag to add:
\begin{lstlisting}
table mTag_table {
  reads {
    ethernet.dst_addr : exact;
    vlan.vid : exact;
  }
  actions {
    // At runtime, entries are programmed with params for the mTag action
    add_mTag;
  }
  max_size : 20000;
}
\end{lstlisting}
\texttt{reads} lists match fields and match types; \texttt{actions} lists possible actions; \texttt{max\_size} the number of entries. This lets the compiler decide how much memory, and which type (TCAM or SRAM), the table needs. Other tables used by the control program:
\begin{itemize}
\item \texttt{source\_check}: reads whether an mTag was parsed and \texttt{metadata.ingress\_port}; actions \texttt{fault\_to\_cpu} (inappropriate mTag), \texttt{strip\_mtag} (strip and record in metadata), or \texttt{pass}. One rule per port (\texttt{max\_size 64}).
\item \texttt{local\_switching}: checks whether the destination is local; on a miss, go to the mTag table.
\item \texttt{egress\_check}: verifies egress is resolved; does not retag packets received with a tag.
\end{itemize}

\subsection{Action specifications}
P4 programs declare action functions built from primitives. P4 \textbf{assumes parallel execution of primitives within an action function} (switches that cannot may emulate this). Parameters (e.g., \texttt{up1}) are supplied by the matching table entry at run time.
\begin{lstlisting}
action add_mTag(up1, up2, down1, down2, egr_spec) {
  add_header(mTag);
  // Copy VLAN ethertype to mTag
  copy_field(mTag.ethertype, vlan.ethertype);
  // Set VLAN's ethertype to signal mTag
  set_field(vlan.ethertype, 0xaaaa);
  set_field(mTag.up1, up1);
  set_field(mTag.up2, up2);
  set_field(mTag.down1, down1);
  set_field(mTag.down2, down2);
  // Set the destination egress port as well
  set_field(metadata.egress_spec, egr_spec);
}
\end{lstlisting}
So the switch inserts the mTag after the VLAN tag, copies the VLAN EtherType into the mTag (to say what follows), and sets the VLAN EtherType to \texttt{0xaaaa} to signal an mTag. The inverse (strip) action is not shown.

\textbf{Primitive actions:}
\begin{itemize}
\item \texttt{set\_field} --- set a header field to a value (masked sets supported);
\item \texttt{copy\_field} --- copy one field to another;
\item \texttt{add\_header} --- make a header instance (and all its fields) valid;
\item \texttt{remove\_header} --- delete (``pop'') a header and its fields;
\item \texttt{increment} --- increment or decrement a field;
\item \texttt{checksum} --- compute a checksum over some header fields (e.g., IPv4).
\end{itemize}
Most switches will only allow header modifications consistent with the declared packet format.

\subsection{The control program}
\key{Once tables and actions are defined, the only remaining task is to specify the flow of control from one table to the next}, using functions, conditionals and table references.
\paperfig[0.55]{p4_fig4_mtag_flow}{Control flow for the mTag example on an edge switch.}
\begin{lstlisting}
control main() {
  // Verify mTag state and port are consistent
  table(source_check);
  // If no error from source_check, continue
  if (!defined(metadata.ingress_error)) {
    // Attempt to switch to end hosts
    table(local_switching);
    if (!defined(metadata.egress_spec)) {
      // Not a known local host; try mtagging
      table(mTag_table);
    }
    // Check for unknown egress state or bad retagging with mTag
    table(egress_check);
  }
}
\end{lstlisting}
\begin{enumerate}
\item \textbf{Source check:} verifies the packet is consistent with the ingress port (mTags should only appear on ports to core switches); strips an mTag and records in \emph{metadata} that the packet had one, so later tables avoid retagging.
\item \textbf{Local switching:} a miss means the destination is not a locally connected host\ldots
\item \ldots so the \textbf{mTag table} is applied to add the tag for the core.
\item \textbf{Egress check:} handles both local and core forwarding; an unknown destination triggers a notification up the SDN control stack.
\end{enumerate}

\section{Compiling a P4 program}
For a network to run a P4 program, \key{we need a compiler to map the target-independent description onto the target switch's specific hardware or software platform}, allocating resources and generating device configuration.

\subsection{Compiling packet parsers}
For programmable parsers, \key{the compiler translates the parser description into a parsing state machine}; \key{for fixed parsers, the compiler merely verifies that the parser description is consistent with the target's parser}. Each state-table entry gives the current state, the value to match, and the next state:
\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Current state} & \textbf{Lookup value} & \textbf{Next state} \\
\midrule
vlan & 0xaaaa & mTag \\
vlan & 0x800 & ipv4 \\
vlan & * & stop \\
mTag & 0x800 & ipv4 \\
mTag & * & stop \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Compiling control programs}
The imperative control flow is convenient but does not expose dependencies or concurrency. So \key{the compiler analyses the control program to identify dependencies and look for opportunities to process header fields in parallel}, and \key{finally generates the target configuration for the switch}. It follows the \key{two-stage} process: \key{it first converts the P4 control program into an intermediate table dependency graph, which it analyses to determine dependencies between tables. A target-specific back-end then maps this graph onto the switch's specific resources.} Targets include software switches, multicore software switches, NPUs, fixed-function switches and RMT pipelines. How mTag maps to each:
\begin{itemize}
\item \textbf{Software switches:} full flexibility; the compiler maps the mTag table graph directly to switch tables, using table types to constrain widths, heights and match kind (exact/prefix/wildcard), possibly with software data structures for ternary/prefix matching.
\item \textbf{Hardware with RAM and TCAM:} hashing in RAM for exact matching (the edge mTag table); the core mTag table, which matches a subset of tag bits, goes in TCAM.
\item \textbf{Switches with parallel tables:} the compiler detects dependencies and places tables in parallel or series; \texttt{mTag\_table} and \texttt{local\_switching} can run in parallel up to the action that sets the mTag.
\item \textbf{Switches that apply actions only at the end of the pipeline:} intermediate stages produce metadata used for the final writes (e.g., whether to add or remove the mTag).
\item \textbf{Switches with few tables:} many P4 tables map onto fewer physical tables (e.g., merge local switching with the mTag table); at run time the compiler's \emph{rule translator} composes the rules of the two logical tables into rules for the single physical table.
\end{itemize}

\section{Conclusion}
OpenFlow gives a single vendor-agnostic API, but targets fixed-function switches with a predetermined set of header fields and actions. P4 is a first step toward switches whose functionality is specified, and may be changed, in the field: the programmer decides how the forwarding plane processes packets, and a compiler turns the imperative program into a TDG mappable to many targets. It is a strawman for \textbf{OpenFlow 2.0}; congestion-control primitives, queuing disciplines and traffic monitoring remain undefined.

\section{Revision checklist}
\begin{itemize}
\item \textbf{P4 vs.\ OpenFlow:} P4 \emph{configures} the switch (parser, tables, control flow); OpenFlow-style APIs \emph{populate} tables. P4 works with OpenFlow, not instead of it.
\item \textbf{Goals:} reconfigurability (in the field), protocol independence (parser + typed tables), target independence (compiler).
\item \textbf{Model vs.\ OpenFlow:} programmable (not fixed) parser; stages in series \emph{or parallel}; protocol-independent primitives.
\item \textbf{Ingress} decides egress port(s) and queue (forward, replicate, drop, flow control); \textbf{egress} does per-instance header changes.
\item \textbf{Metadata:} ingress port, destination/queue, timestamp, table-to-table data (e.g., virtual network ID).
\item \textbf{TDG:} nodes = tables, edges = field/action/control dependencies; decides parallelism (routing $\rightarrow$ ARP must be sequential).
\item \textbf{Program parts:} headers, parsers, tables (\texttt{reads}/\texttt{actions}/\texttt{max\_size}), actions (primitives in parallel), control program.
\item \textbf{mTag:} 32-bit, four 1-byte fields; VLAN EtherType \texttt{0xaaaa} signals mTag; each core switch reads one byte.
\item \textbf{Compiler:} parser $\rightarrow$ state machine (or check vs.\ fixed parser); control program $\rightarrow$ TDG $\rightarrow$ target back-end (RAM/TCAM placement, parallel tables, end-of-pipeline actions via metadata, table merging via rule translator).
\end{itemize}
